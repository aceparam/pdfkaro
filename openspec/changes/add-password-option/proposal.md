# Proposal

## Why

Protect with a password (`/protect-pdf`) is the next Phase 1 tool in catalogue order: the first of the "Protect" group, after Sign PDF closed "Edit and sign". Its working area needs a place to type the new password the file will be locked with. The widget has four kinds of option (a choice, a text, a drawing and a picture), and none of them fits: a text is shown as typed, kept in the widget's state and checked against the standard fonts, while a password must be hidden, must never enter the widget's state (`src/widget/state.ts` promises it never holds a password), and has no way back if it is mistyped. `SPEC.md` "Build phases" rule 3 says a tool that needs a new shared component adds it in its own pull request first, as `add-tool-options`, `add-text-option`, `add-option-conditions`, `add-drawing-option` and `add-picture-option` did. This change is that shared part: a new password, with no tool using it yet. `add-protect-pdf` follows it.

## What Changes

- **A fifth kind of option, a new password,** declared in the registry by its words only: a key, the first field's label, the second field's label, a hint, the sentence tied to the main button while the first field is empty, the sentence tied to it while the second is not yet filled in, and, if the tool wants its own, the sentence for a password its engine refuses.
- **Typed twice, both hidden.** Two password fields, one under the other: the password, then the same password again. The main button waits until both hold the same password. A field that shows the password on request (a "Show password" button) was considered and not chosen; the design gives the reasons. In short: a mistyped password locks the visitor out of their own file for good, with no reset; the fields never turn into visible text, so no phone keyboard corrects or capitalises them, form restore does not keep password fields in current Chrome, Firefox and Safari (the browser's password manager is a separate exception, below), and nobody nearby reads them; and two plain fields need no extra button or announcement.
- **What a password takes is written once,** in `src/widget/option-values.ts`, beside texts, drawings and pictures: each tool's most characters and character rule, by tool id and key. The widget looks it up there, and a tool's engine checks what it is sent with the same function. The registry test checks each new password has its line and the reverse.
- **One character rule for now, printable ASCII:** the letters A to Z and a to z, the numbers 0 to 9, spaces, and the 32 ASCII marks (U+0020 to U+007E), with no space first or last. A password is never changed: not trimmed, not composed, not cut. This is the only set that every PDF reader is sure to turn into the same bytes. With 256-bit AES the password's UTF-8 bytes are what counts, and readers differ on whether they normalise other characters first (Adobe applies SASLprep; PDF.js and qpdf do not), so a password with "é" or Hindi letters could open in one reader and not in another. The rule also catches a keyboard left on another layout, which typing twice alone would not. Allowing other scripts is a question for the owner (below).
- **The most a tool may allow is 127 characters,** the format's own limit for a 256-bit key (longer passwords are cut to 127 bytes by every reader); the registry test checks each tool's limit is from 1 to 127. There is no shortest length beyond one character (the agent's choice, named below).
- **What is wrong is said, never the password.** Every sentence about a password is fixed words: no sentence, status message or error ever holds the password, any part of it, its refused characters or its length. "Some characters cannot be used. Use only the characters listed under the box." (the hint states the rule); "A password cannot start or end with a space."; "This password is too long. Use 127 characters or fewer." (the tool's own limit); "The two passwords are not the same. Type the password again in this box.". A problem with the first field is shown between its label and the field, as a text's is. A space at the end is the one exception: while focus is in the first field it holds the main button quietly, with the tool's sentence under the button only, and its sentence is shown only when focus leaves the first field, on Enter, or when the main button is pressed, so typing "open sesame" one key at a time never flickers an error through "open ". A space first is shown at once; "not the same" is shown the same way by the second field, only once the second field is no longer the start of the first, so it does not appear while the visitor is still typing. While the second field is empty or still the start of the first, the main button waits quietly with the tool's sentence under it.
- **The fields' markup.** No name and no form, so neither is ever submitted to an address. `type="password"` always. `autocomplete="new-password"`, the token for a password being set, which also tells password managers not to fill in a saved one (the agent's choice, named below with what it lets the browser offer). `enterkeyhint="go"`; no `maxlength`, so a paste is never cut silently. Under the first field, read with it: the tool's hint, then a shared note (draft words for the owner): "The password stays in your browser. This site does not send it anywhere. Your browser may offer to save it or to suggest one. A saved password is kept by your browser and may be copied to your browser account." Its first sentence is the one `SPEC.md` asks of every password field ("States every tool handles", Password needed); it becomes one exported constant that `PasswordField` uses too, with no change to how `PasswordField` looks or behaves. The rest is only in the new component, because `autocomplete="new-password"` lets the browser offer to save or suggest a password, so "It is not sent anywhere" alone would not be literally true.
- **Where the password lives.** Not in the widget's state. `useToolRun` holds both fields' values in its own memory beside the files and input passwords, and the reducer never sees them; the rules decide what holds the main button from them. Kept through Cancel, a failure ("Go back to your file") and "Choose another file" while listing, so a visitor does not type it again; forgotten as soon as a job finishes, by "Start again", by removing the last file, and on `pagehide`, as files are. Only the first field's password goes to the tool worker, with the job; the second never leaves the page. The worker is ended after every job, as now.
- **A password the engine refuses** (which the page should never send) fails with a new failure kind, `password-refused`, and its own sentence with a next step: "The password could not be used. Go back to your file and type it again.", or the tool's own words. "Go back to your file" keeps both fields.
- **Keyboard, screen reader and phone,** as for a text: focus moves to the first field once the file is read when it is the first option; Tab goes first field, second field, then on; Enter in either field does what the main button does, and while it waits the status region says why on every press; the Enter that confirms a word in an input method does not press it. A sentence is said once by the status region when it appears or changes kind, never with the password.
- **A new component folder,** `src/components/NewPasswordField/`, with its CSS Module. `PasswordField`, which asks for an input file's password, looks and behaves as before; only its note's first sentence now comes from the shared constant.
- **Tests:** unit tests for the rule, the checks, the pair rules, the sentences (including a check that no sentence ever holds the password or a piece of it), what holds the main button, what is sent, the new failure, the registry checks with a failing case for each, the component's markup and handlers, and a check that the rule matches the readers: a password made of every character the rule takes encrypts with this repo's qpdf at AES-256 and opens with that password, and no other, in qpdf and in PDF.js. No page shows a new password until Protect, so there is no end-to-end test, no screenshot and no page text here.

### What `add-protect-pdf` will then add

Listed so this change is built to fit, not as part of it:
- the registry entry for Protect with a password in the "Protect" group, with one option, a new password under the key `newPassword` (not `password`, one letter from the worker's `passwords`), its words, and its line in `optionPasswords` (127 characters, printable ASCII). Its hint, next to the field, says the password cannot be recovered ("If you forget it, the file cannot be opened. No one can get it back."), not only the text below the tool;
- the engine, `src/engines/tools/protect-pdf.ts`: one qpdf call that opens the file (with its old password, if it has one, through the existing password flow) and writes it again with 256-bit AES (`--encrypt --user-password=… --owner-password=… --bits=256 --`), the same password for opening and for permissions, every permission allowed, and everything else in the file left as it is. Checked here by experiment (qpdf 12.2.0 in this repo's WebAssembly build, PDF.js 6.5.438): such a file reports R = 6 and AESv3, opens in PDF.js and qpdf with the new password and not with the old one, and passes `qpdf --check`. qpdf refuses an empty permissions password with a 256-bit key; a separate random one would stop the visitor from removing the password later in Adobe Acrobat, which asks for it. So the same password is used for both;
- output name `report-protected.pdf`; old restrictions dropped, as for the page tools (owner, 13 Nov 2026), and the page says so;
- the qpdf call never passes `--cleartext-metadata`, `--allow-insecure` or `--allow-weak-crypto`; a unit test checks the document's title (`/Info`) and its XMP metadata cannot be read as plain text in the result without the password;
- page text: that the password cannot be recovered, that "A short password can be guessed by anyone who has the file.", that a digital signature stops being valid, and that the browser may offer to save or suggest the password and a saved one may be copied to the browser account;
- the Privacy page's facts for Protect, for the agent's draft of it: the password is used only in the browser and its worker and never sent; it is forgotten when the job ends, on "Start again" and when the page is left; the browser may offer to save or suggest it, and a saved one may sync to the browser account; it cannot be recovered;
- the fixtures' rows, the unit tests (the result opened with the new password in qpdf and PDF.js, bookmarks, links, forms and attachments kept), the end-to-end test at 360px and 1280px, and the screenshots;
- the no-upload test with the new password as a secret: a marked password holding a space, `#`, `%` and `@`; it also records page errors and the worker's console (`page.on('worker')`, then the worker's `console` events), and checks the output PDF's bytes do not hold the password;
- the site's Content Security Policy (Phase 1 site work, not yet built) should preferably land before Protect is published, since it is the first page that takes a password the visitor makes up. That is the program manager's call when Protect is planned.

### Scope

- **Shared code only:** the registry type, `src/widget/option-values.ts`, `src/widget/options.ts`, the failure kind, the worker's failure mapping and message check, `useToolRun`, `ToolWorkspace`, the new component folder, and their tests. No tool, page or engine changes.
- **Out of scope:**
  - any tool's password words or limit (Protect's change adds its own);
  - showing the password on request, a strength meter, or a generated password;
  - characters outside printable ASCII (an owner question, below);
  - restrictions (printing, copying, editing) set alongside the password: no published tool asks for them, and `SPEC.md` names only the password for Protect;
  - the existing `PasswordField` for opening a protected file, and Unlock PDF.

- "Rules for the code", 1 (one registry) and 2 (engines check what they are sent).

## Where files are processed, and new requests

No file is processed by this change, and no request is added. A typed password stays in the page's memory and goes to the tool worker with the job, by `postMessage`. It is never written to the widget's state, browser storage, the page address, the title, the console or any sentence.

## Open decisions and owner questions touched

- **Shared pieces in tool pull requests** (waiting for the owner): this change follows `SPEC.md`'s rule and gives the new password its own pull request, ahead of Protect.
- **Waiting main buttons** (waiting for the owner): touched in kind. A new password makes the main button wait until both fields match, so Protect joins Rotate, Watermark and Sign PDF on that question's list. Here there is no other way: a starting password chosen by the site would be known to anyone who reads it.
- **"Defaults are set so the main button works without touching any option"** (`SPEC.md` "Tool page anatomy", 4): as for a text, the password is read as the job's input, not an option (the agent's reading, as in `add-text-option`, which the owner can overturn).
- **Licence and source code** (Open decisions): untouched. No dependency is added.

New questions for the owner, each with the default this change uses until answered:
1. **Characters in a password.** Default: printable ASCII only. This is narrower than Watermark's and Sign PDF's Western European rule (issue #20): "é", "ü" and "£" are refused here though Watermark draws them. The reason is different: a password is not drawn but hashed, and with 256-bit AES Adobe first applies SASLprep (which normalises and maps characters) while PDF.js and qpdf use the bytes as typed, so only ASCII is sure to open in every reader. Allow accents and other scripts, at the risk that a file opens in one reader and not in another?
2. **Shortest password.** Default: one character, with no rule. Set a shortest length, such as 8?
3. **The browser's password manager, and the note that says so.** Default: `autocomplete="new-password"`, so a browser may offer to suggest a strong password or to save the one typed (taking a suggestion saves it), and a saved one may sync with the visitor's browser account; that is the browser's own offer, which the visitor accepts or not. `autocomplete="off"` is ignored by Chrome and Firefox for password fields, so it would not stop the offer. Keep it? And are the note's draft words right: "The password stays in your browser. This site does not send it anywhere. Your browser may offer to save it or to suggest one. A saved password is kept by your browser and may be copied to your browser account."? A related line, with no change made: the existing `PasswordField`, which asks for an input file's password, has `autocomplete="off"` and says "It is not sent anywhere."; browsers may still offer to save that password too, so its note has the same gap.
4. **Typed twice, not a "Show password" button.** The agent's choice, for the reasons above. The owner may prefer one field with a button, as GOV.UK's password input has.

No open decision needs more than its assumed default.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `tool-page`: "Options a tool needs" now names the new password among the kinds; a new requirement, "A new password a tool needs", says how the two fields are shown, used by keyboard, screen reader and phone, checked, kept and forgotten; a new requirement, "A new password is used as typed and never said back", says it is sent unchanged and no sentence holds it; a new requirement, "A new password the engine refuses", gives that failure its sentence.
- `tool-registry`: a new requirement, "New passwords are declared in the registry": words only in the registry, the limit and character rule written once and checked by the registry test and the engine, and the rule checked against qpdf and PDF.js.
- `privacy`: a new requirement, "A new password stays in the browser": never in the widget's state, a sentence, storage, the address, the title or the console, only the first copy sent and only to the tool worker, forgotten when the job ends, and a secret in each such tool's no-upload test.

## Impact

- **New code:** `src/components/NewPasswordField/` (component and CSS Module).
- **Changed code:** `src/tools/registry.ts` (`NewPasswordOption`, added to `ToolOption`), `src/widget/option-values.ts` (`PasswordCharacterRule`, `PasswordRule`, `optionPasswords`, empty of tools, `passwordCharacters`, `passwordProblem`, `passwordRule`, `acceptedPassword`, `PasswordRefused`), `src/widget/options.ts` (what holds the main button, what is sent, the sentences; `optionsHold`, `optionsToSend` and `jobOptions` take the extra held inputs as one object, `{ texts?, drawings?, pictures?, pictureTable?, newPasswords?, passwordTable?, typing? }`, in place of more positional arguments, with every existing caller moved to it), `src/widget/format.ts` (`passwordStaysSentence`, "The password stays in your browser.", shared by both password fields), `src/components/PasswordField/PasswordField.tsx` (reads that constant; same words on screen), `src/widget/state.ts` (the `password-refused` kind only; no password in state), `src/widget/failures.ts`, `src/workers/worker-core.ts` and `src/workers/messages.ts` (the new kind), `src/hooks/useToolRun.ts` (holding and forgetting the passwords, sending the first), `ToolWorkspace` (draws the component, ties sentences to the main button, focus), and the registry, options, state, failures, worker, messages and component tests.
- **Other tools:** no change. Every tool with or without options looks and behaves as before; their tests must pass unchanged.
- **Page weight:** the island before a pick is unchanged; the component and rules go in the workspace chunk, fetched after a pick. No WebAssembly is fetched sooner.
